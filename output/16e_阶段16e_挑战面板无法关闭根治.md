# 阶段16e：挑战面板「打开后回不去」根治 + 重连链路一致性修复

> 用户报障原话：**「有一个问题 我打开挑战后 不能返回了 是没有做返回按键吗」**
> 结论：**两个独立事实**——① 原版**确实没有**独立的返回/关闭按钮（全屏遮罩就是设计要求）；
> ② 同时存在一个真 Bug：面板 `state` 永远到不了 `2`，导致**所有**关闭途径（含遮罩）被静默吞掉。
> 本阶段已定位并修复，冷启动 + 重连两条链路实机验证通过，`NullReferenceException` 归零。

---

## 1. 问题拆解

### 1.1 事实一：面板里没有任何「关闭 / 返回 / X」按钮节点（原版设计）

从 APK 里取出面板 prefab 的序列化数据（`assets/bin/Data/e6fbc8443f1094c4f82ba23de40a3e71`，
78116 B，内含 `CAB-ChallengeEntry.prefab`），节点树实测：

```
ChallengeEntry
├─ quanpingzhudang            BoxCollider 960×640   ← 全屏遮罩，绑定 OnCloseClicked
├─ XianShi_3_20
│   ├─ DiBan
│   ├─ Scroll View
│   ├─ Container              BoxCollider 2048×1080 ← 滚动容器，也绑定 OnCloseClicked
│   │     └─ 12 个 XxxZhan 入口节点（各 209×240，绑各自的进入逻辑）
│   └─ Panel
└─ NullBeiJing
```

**整棵树里不存在任何"关闭/返回/X"按钮节点。**
→ 原版的设计就是 **点面板空白处（全屏遮罩）返回**。所以用户"找不到返回键"的感受是对的，
但"回不去"是 Bug，不是设计。

### 1.2 事实二：真正的 Bug —— `state` 永远到不了 2

`MobileGameDemo.ChallengeEntryUI`（`Client_4201.dll`）的 `Close()` 首句就是一道门禁：

```il
=== MobileGameDemo.ChallengeEntryUI::Close  rva=0x11236e  insns=18 ===
  IL_11056f ldc.i4.2
  IL_110570 ldarg.0
  IL_110571 ldfld        field#8055 ᜀ            // this.state
  IL_110576 bne.un.s     0x1105A1               // if (state != 2) -> ret   ← 静默返回
  IL_110578 ldarg.0 / ldfld field#8073 ᜀ
  IL_11057e callvirt     mdef#12245 Hide         // 真正的隐藏
  IL_110583 call         <TypeSpec>::GetSingleton
  IL_11058e callvirt     mdef#12159 Destory2DUI
  IL_110593 ldarg.0 / ldnull / stfld field#8073 ᜀ   // mRootUI = null
  IL_110593 ldarg.0 / ldc.i4.4 / stfld field#8055 ᜀ // state = 4
  IL_1105a1 ret

=== MobileGameDemo.ChallengeEntryUI::OnCloseClicked  rva=0x1123a2  insns=3 ===
  IL_1105a3 ldarg.0
  IL_1105a4 call         mdef#5965 Close          // 遮罩点击 -> Close()
  IL_1105a9 ret
```

而 `state = 2` **只在 `Open()` 的最后一条指令**才被写入：

```il
=== MobileGameDemo.ChallengeEntryUI::Open  rva=0x10fb94  insns=2579 ===
  IL_10dda0 ldc.i4.2 / stfld field#8055 ᜀ          // 进入时先置 2？(见下)
  ...
  IL_1104f3 ... 列表排序 ...
  IL_110566 ldarg.0
  IL_110567 ldc.i4.2
  IL_110568 stfld        field#8055 ᜀ            // this.state = 2  ← 函数最后一条指令
  IL_11056d ret
```

**只要 `Open()` 中途抛异常，`state` 就永远 ≠ 2，`Close()` 变成空操作——
关闭按钮、全屏遮罩、所有返回途径同时失效，形成死界面。**

### 1.3 抛异常的位置：争霸赛（ZBZ）刷新块

```il
  IL_10fae1 ldsfld       field#17854 ᜀ                     // MainPlayer.Object
  IL_10fae6 callvirt     mdef#1926 get_Attribute           // .Attribute
  IL_10faeb ldfld        field#1425 mCCMsgZBZInfo          // ← 这里为 null
  IL_10faf0 callvirt     NetProto.CCMsgZBZInfo @Msg::get_TrunOn()

```

`mCCMsgZBZInfo` 的**唯一写入点**是消息处理器：

```il
=== ᝁ::OnCCMsgZBZInfo  rva=0x27b959  insns=15 ===
  IL_279b5a ldsfld       field#17854 ᜀ                 // MainPlayer.Object
  IL_279b5f brfalse.s    <ret>                        // null -> 直接返回
  IL_279b61 ldsfld       field#17854 ᜀ
  IL_279b66 callvirt     mdef#1926 get_Attribute
  IL_279b6b ldarg.1                                   // 收到的 body
  IL_279b6c ldnull
  IL_279b6d call         MethodSpec GameManager::DeserializeProtobuf<NetProto.CCMsgZBZInfo>
  IL_279b72 stfld        field#1425 mCCMsgZBZInfo     // ← 唯一的赋值
  IL_279b81 ldc.i4       666 / CreateEvent / SendEvent   // 广播事件 666
  IL_279b90 ldc.i4.1 / ret
```

**服务端从未下发 msgid 4602 → `mCCMsgZBZInfo` 恒为 null → `Open()` 在争霸赛块 NRE
→ `state` 永不置 2 → 面板锁死。**

### 1.4 完整根因链

```
服务端不发 4602
   ↓
MainPlayerAttribute.mCCMsgZBZInfo == null
   ↓
ChallengeEntryUI.Open() 在争霸赛刷新块读 .get_TrunOn() → NullReferenceException
   ↓
Open() 中断（第 2579 条指令 this.state = 2 没执行）
   ↓
Close() 首句 if (state != 2) return  →  直接返回
   ↓
全屏遮罩点不动、无返回按钮  →  「打开挑战后回不去」
```

旁证：`OnZhengBaZhan`（争霸赛入口点击）读同一个字段，点击同样 NRE。

## 2. 修复（3 处，服务端全改）

### 修复 A：补发 4602 `CCMsgZBZInfo`（且 body **必须非空**）

新增 `build_zbz_info()`（`server/game_server.py`）：

```python
ZBZ_TURN_ON = False        # False = 未开启赛事（原版非赛事日的正常状态）
ZBZ_TURN_ON_DAY = 0

def build_zbz_info(turn_on=None, turn_on_day=None):
    on = ZBZ_TURN_ON if turn_on is None else turn_on
    day = ZBZ_TURN_ON_DAY if turn_on_day is None else turn_on_day
    b = proto.v_field(1, 0)                      # CurState
    b += proto.v_field(2, 0)                     # CurTargetPlayerID
    b += proto.v_field(3, 0)                     # XingJi
    b += proto.v_field(4, 0)                     # JiFen
    b += proto.v_field_raw(5, 1 if on else 0)    # TrunOn   ← 显式写出
    b += proto.v_field_raw(6, day)               # TrunOnDay
    b += proto.v_field_raw(11, 0)                # HadDefense
    return b
```

> ⚠ **踩坑记录**：`proto.v_field(f, 0)` 返回 `b""`（protobuf 默认值不序列化），
> 8 个字段全为 0 时 body 就是 **0 字节**，帧长只剩 10（纯帧头）。
> 而客户端走的是 `GameManager.DeserializeProtobuf<T>(byte[], ?)`（rva=0x97de0）
> `→ ProtoBuf.Meta.TypeModel::Deserialize(object, ?, Type)`，
> **空流反序列化的返回值是不确定的**（可能返回 null）。
> 故新增 `proto.v_field_raw()` 强制写出 `tag+0`，body 稳定为 6 字节
> `28 00 30 00 58 00`，语义与全默认完全一致，但不再依赖该不确定行为。

下发位置（msgid 102 分支，`server/game_server.py`）：

```python
self.send(103, build_set_main_city_born_pos(*BORN_POS))
self.send(102, build_main_player(...))
self.send(201, build_formation())
self.send(450, build_resource_fb_update())
self.send(4602, build_zbz_info())        # ← 新增；必须在 102 之后
```

（`OnCCMsgZBZInfo` 首句检查 `MainPlayer.Object != null`，所以必须排在 102 后面。）

### 修复 B：601 重连通道补齐「登录态」推送

**这是本阶段最容易漏掉的一环。** 实测发现：**杀服务端重启后，客户端不会重走登录，
而是走 `C→S 601 CCMsgReConnect → S→C 901`**——而 901 的 body 只带 player 本体，
**完全不含** 201 / 450 / 4602 这些独立推送消息：

```
[22:04:02] << 收到 msgid=601(C→S CCMsgReConnect) account='local' sdkNo=1002
[22:04:02] >> 发送 msgid=901(CCMsgReConnect_Ret) 帧长=929
[22:04:02] << 收到 msgid=2001 / 2002 / 703 / 701 / 201 / 1902 / 1912 / 1916 / 2310 / 1801
[22:04:03] << 收到 msgid=103  → 直接进主城（102 分支根本没执行）
```

→ 只改 102 分支的话，**用户重启模拟器 / 断线重连后依然会踩到同样的死界面**。
已在 601 分支补齐：

```python
self.send(901, build_reconnect_ret(RECONNECT_RESULT, self.account, ...))
self.send(201, build_formation())          # PVE 布阵（缺了进副本 NRE）
self.send(450, build_resource_fb_update()) # 资源副本数据（缺了挑战/前往按钮无响应）
self.send(4602, build_zbz_info())          # 争霸赛（缺了挑战面板锁死）
```

### 修复 C：901 与 102 的玩家数据必须一致（等级 + 角色序号）

实测重连后**副本入口的等级门禁被重置**（16e_D 截图：致命游戏/命运之镰/挑战赛全部上锁）：

```python
# 修复前
def build_player(account="local", guid=1, level=1, main_role_index=1):
# 修复后
def build_player(account="local", guid=1, level=None, main_role_index=1):
    if level is None:
        level = PLAYER_LEVEL          # = 30

def build_reconnect_ret(result=1, account="local", svr_time=None,
                        level=None, main_role_index=None):   # ← 新增两个参数
```

并在 `Client` 侧统一来源：

```python
PLAYER_LEVEL = 30   # 全局唯一真源：102(登录) 与 901(重连) 必须发同一个值
self.level = max(int(_SAVE.get("level", 0)), PLAYER_LEVEL)

@property
def main_role_index(self):
    """1=黑剑士(res 18)  2=闪光骑士(res 19)，与 CreateRoleSetup.txt 的选择ID 0/1 对应"""
    return 1 if self.res_id == 18 else 2
```

调用点：
- 601：`build_reconnect_ret(..., level=self.level, main_role_index=self.main_role_index)`
- 102：`build_main_player(..., level=self.level)`
- UDP `mp`：`build_main_player(..., level=CURRENT_CLIENT.level)`

> 根因：`save.json` 里 `"level": 1`，而 102 路径走的是 `build_main_player` 的默认 `level=30`，
> 901 路径走 `build_player` 的默认 `level=1` —— 两条路长期不一致，
> `mainRoleIndex` 同理（901 恒发 1，而本存档角色是 res 19 → 应为 2，
> 这还会让"次日登录奖励"的 `PrizeInfoItems[mainRoleIndex-1]` 取错角色）。

## 4. 环境侧发现（影响复现，非游戏 Bug）

冷启动客户端存在**概率性早崩**（本阶段遇到 2 次）：

```
F/mono (pid): * Assertion at mini-arm.c:2625, condition `pdata.found == 1' not met
I/Zygote: Process xxx exited due to signal 6 (Aborted)
```

崩点在 `CreateOneClient → connect success → StartReceive → received one message` 之后，
即**收到 INIT 应答、开始处理网络消息**时，Mono 在 **houdini（ARM→x86 转译）** 下
做异常栈展开找不到 `.pdata` 条目 → SIGABRT。历史日志 `logs_q3/q4/q5.txt`（9/30 开发期）
也有同样断言，`logs_q6.txt` 之后消失 —— 属**转译缓存冷抖**。

**处置**：写 `work/relaunch_until_alive.py`（force-stop → 启动 → 等 50 s → `pidof` 判定），
实测第 1~2 次重试即可稳定存活。这是环境问题，**不是服务端协议问题**（同一次 INIT 应答在
稳定后完全正常）。
