# 阶段 16g：出战阵容空白根治 + 命运之镰副本全链路打通

日期：2026-10-01 ~ 2026-10-02
状态：**主要链路全部打通**（客户端自发消息驱动，无需人工注入），1 项残留（胜利结算窗时机）

---

## 1. 起点问题

用户报障：主城「挑战 → 命运之镰 → 简单 → 挑战」打开**出战阵容**后，武将列表 **Count=0 全空白**；
点「全部/攻击/防御/辅助」任一标签必抛

```
NullReferenceException at EmBattleSystem.RefreshWuJiangContainer(Int32)
  ← EmBattleSystem.ᜀ(GameObject)   ← UIEventListener.OnClick
```

上一轮（16f 末）已能用 UDP `raw 201` 手工补一条布阵消息让列表显示，但那是外挂注入，
不是客户端真实链路。本阶段目标是**让客户端自己走通**。

---

## 2. 根因链（IL 证据）

### 2.1 出战阵容的 `CurrentInfo` 是谁赋的

`EmBattleSystem`（typedef#948，全类 IL↔RVA 固定差 `D=0x1DF4`）：

| 成员 | mdef | RVA | 作用 |
|---|---|---|---|
| `Open` | 6406 | 0x126068 | 936 IL；`IL_1247d7 call mdef#6410` 填列表 |
| `ᜀ` | 6410 | 0x127224 | 1981 IL；真正填充 `F#8864 List<WuJiangInfo>` 的方法 |
| `ᜀ`(标签) | 6413 | 0x129064 | 战力合计 |
| `ᜀ`(标签点击) | 6433 | 0x12d94c | 80 IL；按 `parent.name`（QuanBu/GongJi/FangYu/FuZhu/YongBin）分派 |
| `RefreshWuJiangContainer` | 6434 | 0x12da58 | 446 IL；切页刷新 |

`ᜀ`(6410) 第一条实质指令就依赖静态字段：

```
IL_125431  ldsfld  field#8709  EmBattleSystem.CurrentInfo   (EmBattleInfo)
IL_125436  ldfld   field#1304  mType
IL_12543b  ldc.i4.s 38
```

`field#8709 CurrentInfo` 为 **null** → NRE → `ᜀ()` 中断 → `F#8864` 列表从未填充 →
界面只剩 5 个空容器框；随后点标签时 `RefreshWuJiangContainer` 也 NRE。

### 2.2 `CurrentInfo` 的唯一写入者在 `UIModulesManager::ᜀ`

`UIModulesManager::ᜀ`（mdef#11110, rva=0x226c10, 3801 IL）是巨型事件分派器：

```
IL_225c7f  ldsfld  field#17854   ᜀ (MainPlayer 单例)
IL_225c84  ldfld   field#1769    mCompleteMember        (MainPlayerCompleteMember)
IL_225c89  ldfld   field#1636    CLONEZHAN_Attack       (EmBattleInfo)
IL_225c8e  stsfld  field#8709    EmBattleSystem.CurrentInfo
IL_225c93  ldloc.0
IL_225c99  callvirt mdef#6406    EmBattleSystem.Open
```

**整个程序集只有这一处调 `EmBattleSystem.Open`**。
其余 case 只 `stsfld CurrentInfo`，不 Open。
所以「命运之镰」要打开阵容，必须让事件里的 `eFormationType` 命中那个 case。

### 2.3 客户端其实一直在发请求 —— 是服务端没回

抓服务端日志发现客户端在进入阵容前**自发**发送：

```
收到 msgid=201  CMsgRequestFormation{type=10, wj=[hero18,hero19,hero19,hero18,hero19]}
```

`CMsgRequestFormation` 契约（`work/messages_full.json`）只有一个字段 `type` —— **C→S 201 是"请求布阵"**，
而服务端原实现里 201 只出现在 S→C 方向（登录时推一条 type=0），**从来没处理过 C→S 201**，
于是 `CurrentInfo` 永远是 null。

### 2.4 `eFormationType` 枚举（从 `carved/CAB-Protobuf_00002231.dll` 导出）

| 值 | 名称 | 含义 |
|---|---|---|
| 0 | PVE | 主线副本 |
| 10 | **ScytheOfFate** | 命运之镰 |
| … | … | （完整表见 `work/` 内 `dump_enum.py` 输出） |

`201` 的 S→C 处理器 `ᝁ::OnEmBattleUpdateFromServer`（mdef#12965, rva=0x26fbe4, 1600 IL）
按 `CMsgFormation.type` 做 switch，命中 case 后写入
`mCompleteMember` 上对应的 `EmBattleInfo`（PVEEnBattle / ScytheOfFateEnBattle …）的
`mType / mMainCommander / mPioneer1 / mPioneer2 / mBackUp1 / mBackUp2`。

**这就闭合了**：客户端请求 type=10 → 服务端回 type=10 的 201 →
`ScytheOfFateEnBattle` 被填好 → 事件分派把它塞进 `CurrentInfo` → `Open` 正常渲染。

## 3. 修复（服务端 `server/game_server.py`）

### 3.1 C→S 201 应答（核心修复）

```python
DEFAULT_FORMATION = ("hero18", "hero19", "hero19", "hero18", "hero19")

def build_formation(type_=0, wj=None):
    """S→C 201 CMsgFormation{1:type(eFormationType), 2:wj(repeated str)}"""
    ...

def parse_formation(body):
    """C→S 201 CMsgRequestFormation{1:type} -> (type, [guid...])"""

elif msgid == 201:
    t, wj = parse_formation(body)
    self.set_formation(t, wj)
    self.send(201, build_formation(t, wj))
```

`set_formation` 会持久化到 `server/save.json`，重连（901）后仍一致。

### 3.2 C→S 331 进入资源副本

```python
elif msgid == 331:                       # CCMsgResouceFBRequest{level=难度}
    lv = parse_int_field(body, 1)
    self.send(107, pb_int_field(1, SCYTHE_OF_FATE_REGION))   # 60
```

IL 依据（`EmBattleSystem::ᜁ` rva=0x12b918）：`if (mType == 10) Send(331, ...); Close();`

**命运之镰 = Region id 60**（`work/apk/luapack_extracted/GameData/RegionList.txt`，
type=10，资源 `Scene_C_01`；与阶段13 用的 3010 同一场景资源）。

### 3.3 C→S 332 结算上报 → S→C 1001

```python
elif msgid == 332:
    res = parse_int_field(body, 1)       # 1胜 2败
    self.send(1001, build_fb_result(res, 3 if res == 1 else 0))
```

IL 依据（`ScytheOfFateController`，rva=0x42b70 胜 / 0x42ad0 败）：
`if (mRegionType==10) { m.result = 1|2; m.starCount = 3 - GetMemberDeadCount(); Send(332, m); }`

### 3.4 编码坑：1001 必须用 **varint**

`work/messages_full.json` 里 `CCMsgResultFB` 的 `dataFormat=2` 一度被当成 fixed32，
实测**两种编码客户端都能解析但行为不同**：

- `proto.f32_field` 编码 → 客户端静默丢弃，**不弹结算窗**
- `proto.v_field`（varint）编码 → 正常弹窗

结论：与阶段16d 一致，**protobuf-net 的 `ReadInt32` 对 varint/fixed32 都接受**，
但本项目结算链实测以 **varint** 为准。`build_fb_result` 已改为 varint。

## 5. 残留问题（已定位，未根治）

### 5.1 胜利结算窗时机

- 现象：332 之后再补 1001 → 客户端**静默丢弃**，不弹窗；
  但在**倒计时未归零时**主动发 1001 → 倒计时归零瞬间正常弹出「挑战成功」。
- 机理：`ScytheOfFateController::Update`(rva=0x412fc) 注册了事件 111 的两个监听器
  （mdef#1048 / #1050）；客户端超时上报 332 后**监听器已被拆卸**。
  真正的胜利窗入口是 `mdef#1051`：事件111 → `PostEvent(118, StarCount = 3 - 阵亡数)`。
- 已实施 workaround：服务端收到 104（region=60）后 `schedule_fb_result()`，
  在 **83s** 处主动推送 `1001{result=1, star=3}`，赶在 90s 倒计时结束前到达。

### 5.2 其他已知残留（沿用前序阶段）

- `GetSpecialGoodsViewSystem` 的 NRE（1204「获得武将」提示链，`CurrentInfo` null）
- 主城偶发浅蓝无地面：`mp` 重发 103+102 可复位
- 主城手动移动（点地板/摇杆）仍不响应
- JJC 预赛窗每次登录弹（X → 退出挑战赛 两步关闭）
- 副本「今日剩余次数/冷却」由 450 `CCMsgResouceFBDataUpdate` 维护，尚未做真实扣减
