# 阶段16f：主城物理复位与「挑战」入口链路打通

> 日期：2026-10-01 深夜
> 起始问题：用户「继续推进下一步」——延续 16e（挑战面板无法关闭已根治）之后
> 核心结论：**一个属性引号风格的解析 bug，让主城出生点恒为 `(0,0,0)`，导致角色悬空、物理失效、主城场景不渲染、所有入口点击无效。修复后一次性打通了「挑战」面板 → 副本二级界面 → 出战阵容 的完整链路。**

---

## 一、核心发现：`get_region_born_pos` 只认双引号

### 现象
- 主城画面**纯浅蓝无任何地面/建筑**（历史遗留问题，此前被归因于"场景美术未渲染"）
- `logcat` 每帧刷屏：`Touch floor failed!!!`
- 点「挑战」面板里的「致命游戏」入口 **无任何反应**

### 定位过程
1. 反汇编 103 的 handler `ᝁ::OnSetMainCityBornPos`（rva=0x26ed7c，仅 14 条 IL）：
   ```csharp
   CCMsgVector3 v = Deserialize<CCMsgVector3>(body);
   ᝁ.ᜀ = new Vector3(v.x, v.y, v.z);   // 只存静态字段 field#17855
   return 1;
   ```
   → **103 不直接设置位置**

2. 扫 `field#17855` 引用，只有 4 处。真正消费它的是 `ᝁ::OnQuestFirstEnterRegionRet`（**102 的 handler**，310 条 IL）：
   ```csharp
   local3 = CurrentRegion.getRegionType();
   if (local3 == 11)  MainPlayer = CreateUnit(dynID, 2, res_id, CurrentRegion.get_BornBos(), ...);
   else               MainPlayer = CreateUnit(dynID, 2, res_id, ᝁ.ᜀ /* = 103 存的值 */, ...);  // IL_26d04b
   ```
   → **103 必须在 102 之前送达，且只有走 102 才会被消费**

3. 检查服务端实际下发的 103：`body = 0d 00000000 15 00000000 1d 00000000` → **(0, 0, 0)**
   而主城地面在 **y ≈ 301.5**

4. 追 `BORN_POS` 来源 → 命令行 `--born-pos` 默认 `"0,0,0"`。
   服务端已有 `get_region_born_pos(region_id)` 会从 `GameData/RegionLogic/<id>_gk.xml` 的 `<BornBos>` 读，**但主城路径没用它**。

5. 验证 `get_region_born_pos(1)` → **返回 `None`**！
   而 `get_region_born_pos(3010)` → 返回 `(24.0874, 199.6005, 52.64263)` ✓

6. **根因**：正则写死了双引号
   ```python
   r'<BornBos[^>]*PosX="([-\d.eE]+)"...'   # 只认 PosX="..."
   ```
   而主城 `1_gk.xml` 用的是**单引号**：
   ```xml
   <BornBos PosX='-1.12' PosY='301.52' PosZ='15.42' Yaw='180' />
   ```
   全库统计：**369 个 gk 文件里 33 个用单引号**（含主城 region 1）。

### 因果链
```
1_gk.xml 单引号
  → get_region_born_pos(1) = None
  → 102 回退 BORN_POS = (0,0,0)
  → CreateUnit 把角色放在 y=0，而主城地面在 y≈301.5
  → 每帧 Raycast 打不到地板 → "Touch floor failed!!!"
  → 角色物理失效：不能移动、相机跟随到场景外（看到纯浅蓝背景）
  → 挑战入口设了导航目标也走不动 → 点了没反应
```

## 二、修复（3 处，全在服务端，无客户端补丁）

### A. `get_region_born_pos` 同时支持两种引号
```python
m = _re.search(r"""<BornBos[^>]*PosX=["']([-\d.eE]+)["'][^>]*PosY=["']([-\d.eE]+)["']"""
               r"""[^>]*PosZ=["']([-\d.eE]+)["']""", txt)
if not m:
    def attr(name):
        mm = _re.search(r"""<BornBos[^>]*%s=["']([-\d.eE]+)["']""" % name, txt)
```
验证：`region 1/2/3/1001/3010` 全部正确解析，主城 = `(-1.12, 301.52, 15.42)`。

### B. 主城出生点改为自动读取（`--born-pos` 默认 `auto`）
```python
ap.add_argument("--born-pos", default="auto",
                help="auto=自动读 GameData/RegionLogic/1_gk.xml 的 <BornBos>（原版真值）")
...
if args.born_pos.strip().lower() == "auto":
    BORN_POS = get_region_born_pos(1) or (0.0, 0.0, 0.0)
    log("主城出生点（auto，来自 1_gk.xml BornBos）= %s" % (BORN_POS,))
```

### C. 601 重连分支补发 103
```python
self.send(103, build_set_main_city_born_pos(*BORN_POS))   # 在 901 之后、201 之前
```
> 注：`OnReConnectRet`（901 handler，仅 42 条 IL）只做 `UnPackData` + `SyncServerTime`，
> **不重建角色、不设位置**，所以重连路径的 103 实际不被消费（保留作为状态占位，无害）。
> 重连后位置修正的真正手段是**冷启动走 102**。

## 四、新打通的关键链路 ★

### 4.1 挑战面板入口的架构真相（重要）
反汇编 `ChallengeEntryUI` 的 14 个按钮绑定（`Open()` 中 `field#NNNN → FindChild → ldftn OnXxx`）：

| 绑定字段 | handler | 入口 |
|---|---|---|
| #8058 / #8072 | `OnCloseClicked` | 全屏遮罩 ×2 |
| #8059 | `OnSiWangDuoBi` | 死亡解脱 |
| #8060 | `OnJingXiangTiaoZhan` | 镜像挑战 |
| #8070 | `OnCloneZhan` | 克隆战 |
| #8061 | `OnZhiMingYouXi` | **致命游戏** |
| … | `OnShengDanBiLei` / `OnMingYunZhiLian` / `OnJJC` / `OnTiaoZhanSai` / `OnKuangZhan` / `OnBaiCengTa` / `OnZhengBaZhan` / `OnKuaFuZhan` | 其余入口 |

**关键：入口不是"直接开界面"，而是"自动寻路到主城对应传送门"**。
`OnZhiMingYouXi`（83 条 IL）逻辑：
```csharp
if (MainPlayer.Attribute.mLevel < entry.unlockLevel) return;
if (MainPlayer.Attribute.LastMainFBNormal < entry.unlockAfterMainFBNormal) return;
pos = MainPlayer.GetPosition();
if (|pos - MainCityEntryInfo.ᜀ.mTypeInfo[8].mPos| >= .mRadius)
    PostEvent(CreateEvent(472));                      // 太远
else {
    ev = CreateEvent(1); ev.AddParam(mTypeInfo[8].mPos); ev.AddParam(0.5f);
    MainPlayer.eventReceiver.PostEvent(ev);
    MainPlayer.mCompleteMember.ᜀ = mCurNaviGoal;        // 设置导航目标
}
Close();                                              // 两分支都关闭面板
```

### 4.2 `mTypeInfo` 是按 BindPlayID 索引的
`MainCityEntryInfo::.ctor`（243 条 IL）解析 `1_gk.xml`：
1. 先遍历 `<TriggerList>` → `{TriggerId: Vector4(PosX, PosY, PosZ, Radius)}`
2. 再遍历 `<CityPlayEntryList>` → 对每个 `BindPlayID`（逗号分隔）**各 Add 一项**，指向该入口的 Trigger 位置

`1_gk.xml` 实测内容：
```xml
<BornBos PosX='-1.12' PosY='301.52' PosZ='15.42' Yaw='180'/>
<CityPlayEntry CityPlayEntryID='1' TriggerId='1' BindPlayID='2'          .../>
<CityPlayEntry CityPlayEntryID='2' TriggerId='3' BindPlayID='3,7,25'     .../>
<CityPlayEntry CityPlayEntryID='3' TriggerId='4' BindPlayID='4,5,6,8,9,10,101' .../>
<Trigger TriggerId='4' PosX='-18.43' PosY='301.81' PosZ='34.82' Radius='1.46'/>
```
→ **`mTypeInfo[8]` = PlayID 8 = Trigger 4 = `(-18.43, 301.81, 34.82)`**
   （这解释了 index 8 为何不越界——它不是数组下标，而是 PlayID 键）

### 4.3 完整链路（已实测跑通）
```
点「挑战」(1788,580)  →  挑战面板打开
点「致命游戏」(1330,435) → 面板关闭 + 屏幕提示「自动移动中。。。」
```

## 五、新遗留问题（已深度定位）

### 5.1 出战阵容界面：武将列表为空 → 无法开战
**现象**：点「挑战」→ 打开出战阵容界面（队长/队员×3/支援 五个槽位），
中间武将列表（全部/攻击/防御/辅助 标签）**完全空白**；
点右下开战按钮 → 弹窗「**主将不能为空哦。**」

**已定位的代码事实**：
1. 点标签 → `EmBattleSystem.ᜀ(GameObject)` → `EmBattleSystem::RefreshWuJiangContainer(int type)`（446 条 IL）
   ```csharp
   switch (this.field#8787.ᜀ /* 当前类别索引 */ - 1) {  // -1 时跳过
       case 0: local0 = field#8787.ᜅ; ... }             // 5 个容器 GameObject
   local0.SetActive(false);
   switch (type - 1) {
       case 0: local1 = field#8787.ᜅ;
           for (i=0; i < field#8787.ᜀ.Count; i++) {     // ← 武将列表 field#8864
               wj = list[i];
               if (wj.WuJiangCfg.uType == 2) {           // ← WuJiangCfg 可能为 null
                   if (dict.ContainsKey(wj.Guid)) local2.Add(dict[wj.Guid]);
                   else LogException("3 mWuJiangContainer can't find: " + wj.Guid);
               } } }
   ```
2. `EmBattleSystem.ᜀ`（field#8787）类型是内部类 `ᜊ`（TypeDef#949）
   - `ᜊ::.ctor` 初始化：`ᜀ=new/dict`、`ᜁ=new`、**`ᜀ=-1`（索引，IL_12ef53 ldc.i4.m1）**、`ᜀ=new List`
   - 由 `EmBattleSystem::Open()` 里 `newobj ᜊ::.ctor` + `stfld field#8787`（IL_124287）创建
   - `Open()` 唯一调用者 = `UIModulesManager::ᜀ`（RVA 0x227a99）
3. `WuJiangInfo.WuJiangCfg` 由 `WuJiangInfo::SyncWuJiangInfo(CCMsgWuJiangAllInfoAndJob)` 赋值：
   ```csharp
   this.Index     = msg.index;
   this.WuJiangCfg = GameManager.GetSingleton().GetPropertyCfg(this.Index);
   ```
   `WuJiangPropertyCfgMgr::GetPropertyCfg` = `dict.ContainsKey(id) ? dict[id] : null`
   → 配置表 `WuJiangBaseAttri.ini` **存在且含 18=黑剑士 / 19=闪光骑士** ✓
4. 实测 **无** `mWuJiangContainer can't find` 报错 → 说明**列表本身 Count=0**，不是查表失败

**结论**：`ᜊ.ᜀ`（List<WuJiangInfo>）从未被填充。
**下一阶段方向**：追踪该列表的 Add/Clear 路径，确认 `CMsgWuJiang`(102 tag101) → `WuJiangInfo` 的转换环节；
或考虑 IL 补丁让列表回退读取 `MainPlayer` 的武将数据。

### 5.2 调试期发现的环境陷阱（非游戏 Bug，但会误导排查）
- 用 UDP `mp`（重发 103+102）会让 `OnQuestFirstEnterRegionRet` **重复 CreateUnit**，
  导致 `UnitManager.Update` 每帧抛 `ArgumentException: An element with the same key already exists in the dictionary.`（实测 1621 次），
  **中断 Update → 角色不移动 → 误判为"寻路失效"**。
- 清理方式：**冷启动客户端**（force-stop + start），走一次干净的 102。
- 冷启动偶发早崩 `F/mono Assertion at mini-arm.c:2625 'pdata.found == 1'` → signal 6，
  是 MuMu houdini 转译下 Mono 异常栈展开问题，用 `work/relaunch_until_alive.py` 重试 1~2 次即稳。
