## 4. 网络与协议推断

- **传输层：原生 TCP Socket**（非 HTTP）。证据：`client.bytes` 中 `System.Net.Sockets` 相关成员与自定义缓冲 `BufferRecv` / `ReceiveBufferSize` / `IsNeedSafeEvent`。
  → 我们本地服务端需要写 **TCP 长连接 + 自定义分包**，不是 Flask HTTP 就能搞定（Flask 用于工具/管理界面，游戏主链路用 asyncio TCP）。
- **序列化：protobuf-net**。证据：`ProtoBuf.DataFormat`、`Protocol Buffers for .NET`、`Marc Gravell`、`knownTypes`、`c:\Dev\protobuf-net\...pdb`。
  → 消息以 `[ProtoContract]` 标注的 **.NET 类** 定义，运行时反射序列化。
  → **重大利好**：可用 dnSpy/ILSpy 一次性导出**全部消息结构 + 字段编号**，本地用 Python `protobuf` 逐条复刻；也可直接从 DLL 抽 `.proto`。
- **登录**：UC 渠道 SDK（`ucid.user.login` / `ucid.user.ticket`），本地需免鉴权化。
- **资源更新**：HTTP，路径 `/Android/UpdateRoot/{Version,IncrementPack}`。

### 服务器地址现状：**尚未取得**

全包扫描（516 个条目，URL + IPv4 正则）未发现游戏服务器域名或明文 IP。候选来源按优先级：

1. `client.bytes` DLL 内的 XOR 混淆串 —— 阶段 1 反编译后定位（首选）
2. Lua 脚本中的配置表
3. 原 `Version` 文件（服务器已死，可考虑 WebArchive / 其他渠道包 / 玩家社区留档）
4. **兜底且最可靠**：**根本不需要知道原地址** —— 我们只需找到客户端"取服务器地址"的那一处调用，把它重定向到 `192.168.x.x` 即可。Frida 或补丁都能做到。

→ **不构成阻塞性风险**。

## 5. 可行性结论

### 有利因素（为什么能做）

1. Mono 后端 → C# 近乎源码级可读，这是最大的一笔便宜
2. 无壳、无混淆、无 SSL Pinning、无 TLS、无签名自校验 —— 对抗面几乎为零
3. 客户端自带 31 个关卡场景与全部资源，**不依赖服务器下发内容**
4. protobuf-net 反射序列化 → 消息结构可静态批量导出
5. 有 `Reporter` 运行时日志面板 + 大量中文业务字段名（`ShouKuangCount`、`JieBiao`、`VIPMaxLevel`…）→ 语义推断成本低

### 不利因素（真实成本在哪）

1. **服务端逻辑 100% 缺失**。客户端只有表现层与请求封装，战斗结算/数值/掉落/背包/成长/存档全在服务器。
   → 这不是"转发协议"，而是**重写一个游戏服务端**。这是本项目唯一的大工作量。
2. 需复刻的 protobuf 消息条数未知（预计几十到上百条），需逐条核对字段编号
3. armeabi-v7a 32 位：现代手机可能装不上或需兼容层；建议准备 Android 8~9 的 32 位设备/模拟器
4. UC 渠道登录必须绕行为本地免鉴权
5. 当前沙箱**缺 JDK / adb / apktool / Frida / dnSpy(ILSpy)**，需先补装

### 分项目标判断

| 目标 | 判断 | 说明 |
|---|---|---|
| 启动 | ✅ 可行 | 无壳无自校验，改包重签即可 |
| 登录 | ✅ 可行 | 免鉴权本地账号，跳过 UC |
| 进入游戏 | ✅ 可行（中等工作量） | 需实现登录返回、角色列表/创建、进入场景几个接口 |
| 核心玩法可用 | ⚠️ **部分可行** | 客户端存在 `SkillBuilder` / 战斗相关类 → 战斗很可能是**客户端计算 + 服务器校验/存档**。对我们是利好：本地服务端可先跑"宽容模式"（接受客户端上报），再逐步加校验。玩法深度取决于愿意实现多少服务端逻辑 |
| 存档本地电脑 | ✅ 完全可行 | 服务端自己写，存储方案自由（SQLite/JSON） |

# 附录 A：关于"转成 64 位"的可行性专项评估

**提问**：能否把这个只有 armeabi-v7a 的包转成 64 位（arm64-v8a）？

**结论：理论上存在唯一一条路径，但强烈不建议走——它会摧毁本项目最大的技术优势。**

## A.1 "换 .so" 路线 —— 不可行

| 障碍 | 说明 |
|---|---|
| Unity 4.6 从未发布 arm64 的原生库 | `libunity.so` / `libmono.so` / `libmain.so` 只有 32 位 ARM 版本，官方无 arm64 构建物 |
| 不能混 ABI | Android 一个进程只能加载一种 ABI 的 `.so`，无法"只换 libmono" |
| 网传"改目录名"是错的 | 把 `lib/armeabi-v7a/` 改名成 `lib/arm64-v8a/` 只会让 `dlopen` 失败（ELF class 不匹配） |

## A.2 唯一理论路径：升级 Unity 重新编译 —— 但代价是架构崩塌

Google 官方口径（Android 64-bit 要求文档）：Unity **≤5.6 不支持 64 位**，需升级到 2017.4.16+ / 2018.2+。我们是 4.6.3f1，属于"必须升级"一档。

**然而真正的杀手不是"升级"，而是"升完必须换后端"：**

> Unity 官方文档：*Before you can enable the ARM64 architecture, you must Set the Scripting Backend to IL2CPP. **The Mono backend does not support ARM64**.*

而切到 IL2CPP 对本游戏是**致命**的：

1. **热更新机制直接死亡** —— 本游戏把 `client.bytes`（C# DLL）打包进 AssetBundle，运行时 `Assembly.Load` 动态加载。IL2CPP 是 AOT 静态编译，**不支持运行时加载程序集**。
2. **protobuf-net 受限** —— 它依赖运行时反射与动态代码生成，IL2CPP 下需改为静态 `.proto` 预生成，等于重写全部消息层。
3. **我们失去最大优势** —— 本项目之所以评级 B+，核心就是"Mono 后端 → DLL 可反编译、可打补丁"。一旦 IL2CPP，优势归零，所有改包/重定向手段都要重做。

叠加常规迁移成本：Unity 4.6 → 现代 LTS 的 API 断裂（`Application.LoadLevel` → `SceneManager` 等）、NGUI 重写、shader 重做、`version=9` 旧序列化格式需用 AssetStudio 导出再重新导入、AssetBundle 格式变化。

**定性：这不是"移植"，是"重做"。**

## A.3 关键反问：本项目其实不需要 64 位

- 64 位问题**只影响客户端**。我们要写的本地服务端是 Python，**天然 64 位**，完全不受影响。
- ARM64 硬件本身兼容 AArch32；Android 收紧的是策略而非硬件。现存设备绝大多数仍支持 32 位应用。
- ARM 已宣布 2023 年起移动 Cortex-A 核心全面 64-bit only，但这是**新芯片**的事，存量设备不受影响。
- **PC 安卓模拟器**（雷电 / LDPlayer / BlueStacks，x86 + ARM 指令翻译）能跑 armeabi-v7a，且模拟器与本地服务端同机，联调最方便。

**只有一种情况才真正需要 64 位**：你手上只有一台 64-bit-only 的新旗舰（Pixel 7 之后的部分机型），且不想用模拟器。

## A.4 建议的应对排序（成本从低到高）

1. **用 PC 安卓模拟器**（推荐）—— 零成本，与本地服务端同机，`adb` 抓包/装包都方便
2. **找一台 Android 9~11 的老设备** —— 几十元，最省事
3. 换一台仍支持 32 位的机型 / ROM
4. **重制到现代引擎** —— 只在阶段 1~3 完成、协议与玩法全部摸清后再评估；届时已有完整协议文档与资源，重制确定性会高得多（但仍是一个独立项目量级）

**当前决策：阶段 1 不处理 64 位问题，按 32 位推进。**
